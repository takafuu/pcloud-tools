## 2. 目的と範囲

目的は、複数ファイルの転送における直列待ちを減らし、改善量と失敗率を測定可能にすること。回線速度そのものや単一巨大ファイルの高速化は保証しない。

対象はpublic `pushd|diffd transfer automation-run` と、それを検証するdev fake-rcloneの `executor-run`。manual `real-run` は確認済みの1件だけを実行し、並列数設定で対象を増やさない。preview/check/gateのread-only契約は維持する。

今回はrclone常駐化/RC、接続プール、新プロトコル、bisync高速化、同期scope拡張、暗号化変更を実装しない。archiveは別CLIのまま維持し、既存transfers/checkers/bwlimitの比較は別の測定対象とする。archiveの設定をmanagerへ移さない。

## 3. 設定契約

| 設定 | 型・許容値 | 既定値 | 意味 |
| --- | --- | --- | --- |
| `PCLOUD_TOOLS_PUSHD_TRANSFER_CONCURRENCY` | 整数1〜4 | 1 | pushd内の同時copyto数 |
| `PCLOUD_TOOLS_DIFFD_TRANSFER_CONCURRENCY` | 整数1〜4 | 1 | diffd内の同時copyto数 |

設定は既存の `.env` と `config.py` のFieldSpecへ追加する。優先順位は既存に合わせ、環境変数 > 環境ごとの `.env` > 既定値。初版では専用CLI overrideは追加しない。未指定だけが既定値となり、空文字・非整数・0・負数・5以上はエラー。丸めや無制限指定はしない。不正設定の実行要求は子プロセス起動、startup cleanup、queue/journal更新より前に拒否する。

設定はexecutor起動時に読み、そのtickの途中では変更しない。周期起動する次のtickから新値を使う。既存plistへ並列数を固定注入せず、通常は `.env` を読む。管理者がlaunchd環境へ明示overrideしている場合はそれが優先されるため、status/infoには解決値とsource layerを表示する。

`--max-records` は1 tickの選択件数上限、concurrencyは同時実行上限で別概念。10件/並列2なら同時2件まで、合計10件まで処理する。1件/並列4なら実効同時数は1。pushd=4、diffd=4なら両方向合計最大8プロセス。rclone内部の単一ファイル用stream数を意味しない。

status/info/preview/gateは設定値、実効上限、判明する場合のbatch上限を示す。batch上限が不明なら推測せずunknownとする。doctorは両設定を検証する。help/help --aiと `.env.example` に意味・範囲・既定値・反映時点を反映する。並列数1への変更で次tickから直列へ戻せる。

## 4. 実行と排他

既存gate、shadow report、scope、manual-review、settlingを確認してから、既存順序で最大max-records件を選択する。選択後に新しく入ったrecordは次tickへ残す。選択中のdeferred recordを補うために上限外のrecordを取り込まない。空いた実行枠は、同じ選択集合の次の候補に割り当てる。

転送の待機だけを並列化し、状態変更はexecutor内の一つの制御箇所で直列化する。ただし、それだけでは別processのwatcher/pollerとの競合を防げないため、queue/journalの全read-modify-writeを共通のプロセス間lockで保護する。append、重複処理、prune、consume、clear、backfill、journal更新も対象。atomic replaceだけを排他の代用にしない。read-only readerはatomicな完全snapshotを読めばよい。

同じserviceのexecutor tickは重複実行しない。別起動元からのmanual実行も含め、同一state root内で同じremote/pathを同時に書く転送を防ぐ。path lockの取得から反対方向queue・scope・fingerprintの再確認までを一貫させる。lock競合はdeferredとして保持し、通常のerror通知を送らない。pathの正規化やsymlink/大文字小文字による衝突を安全に判定できない候補は並列実行せず保留する。

ネットワーク待機中にqueue全体のlockを保持しない。path単位の転送排他と短時間の状態更新lockを分け、取得順を固定する。互いを待ち続ける構成にしない。独立したファイルの失敗で他の転送を無条件に中断しないが、状態更新・lock管理が壊れた場合は新しい転送の開始を止め、未確定recordを保持する。

## 5. queueと競合保護

path一致だけで成功recordを削除しない。queueの各変更に識別子 `event_id` を持たせ、選択した世代と現在の世代が一致する場合だけconsumeする。同じpath/actionへの新しい観測は、既存候補へ統合する場合もevent_idを更新する。転送中の新イベントを単なるduplicateとして捨てない。最初の待機時刻と最新観測時刻を区別する。

既存のstring/object形式を読み続ける。event_idのない旧recordは、実行可能なtickでlock下に読み直してから識別子を付ける。previewは識別子を保存しない。既存path/action/reasonと未知のフィールドを保持し、全queueの破壊的変換や初期化はしない。consume APIは旧recordをまとめてpath削除する経路から、選択したevent_idだけの削除へ変更する。

uploadは開始直前のfingerprintを取得し、完了後に再確認する。copytoが成功を返してもsourceが変わっていれば最新候補を残し、変更後のfingerprintを「転送済み」として記録しない。`source file is being updated` は既存どおりsettlingへ戻し、通常エラー通知を出さない。

downloadはattemptごとの一意なstagingを使い、開始直前のdestination fingerprintと反映直前の値を比較する。変更があれば既存localを保持してconflict copyへ保存し、manual-reviewとしてqueueを保持する。新しいremote世代が観測済みなら古い世代を最新完了としてconsumeしない。最終反映、suppression journal、upload-origin journalの整合が確認できるまで成功扱いでqueueを除去しない。

delete/rename/manual-review、hidden/excluded、アップロード由来のecho抑制、ダウンロード由来の再upload抑制を維持する。並列化を理由にローカル・remoteの削除伝播を追加しない。

## 6. タイムアウト・停止・互換性

既存 `PCLOUD_TOOLS_TRANSFER_EXEC_TIMEOUT_SECONDS` は各copytoの起動から適用し、queue待ち時間を含めない。新しい即時retry loopは追加せず、失敗・timeout・deferredは次tickへ残す。

SIGINT/SIGTERM時は新規開始を止め、自分が起動した各process groupを期限付きで終了・回収する。未開始・未確定recordを残し、正常完了を確認できた分だけ確定する。SIGKILL等で親が突然消えるケースは正常cleanupを保証できないため、残存child/attemptの所有と生存を判定できる情報を残す。確認不能なattemptは自動成功・自動lock解除・重複再実行をしない。PID番号だけで他processをkillしない。

queueとlast-transferは既存readerとの互換性を保つ追加フィールド方式とし、既存結果キー・modeを削除/変更しない。旧last-transferに計測値がなくてもstatusは落とさずunknown表示。更新・旧版への切り戻しでは、executorだけでなくwatcher/poller、manual転送、backfill等を含め、同じqueue/journalへ書く全プロセスを停止する。開始済み転送の完了または自分のchildの回収を確認してから一式を切り替える。旧版と新版のwriterを同じqueue/journalに同時接続しない。並列数1への設定変更を通常の切り戻しとし、package downgradeでは追加フィールドの扱いも検証する。

### 6.1 異常終了後の保留と復旧

確認不能なattemptは、statusでattempt ID、対象、保留理由、最後に確認できたphase、所有childの終了確認が必要かを表示する。PIDだけの判定や経過時間だけの強制解除はしない。復旧手順は、同じstateを変更する全writerの停止、attemptと所有childの照合、child終了確認、queueの最新event_idとlocal fingerprintの再確認、再試行可能への明示的な移行の順とする。所有や終了を確認できない場合は保留を維持し、その不足情報を示す。

復旧は成功receiptの捏造やqueue消費ではなく、確認できたattemptの保留を解除して最新候補を再評価可能にする操作とする。実装はread-only確認と明示的な実行を分離し、対象attemptを指定してpreviewできる操作面および手順を提供する。通常起動で確認不能なattemptを勝手に解除しない。公開の操作名・追加フィールドは実装時にhelpと4文書へ同時に確定し、fixtureで検証する。

## 7. 計測

既存last-transferへ `performance` を追加し、その内部にschema version、解決済み並列数、実測peak、batch elapsed、選択/開始/成功/失敗/timeout/deferred/conflict件数を保存する。recordごとにqueue待ち時間、開始/終了UTC、monotonicによる実行秒数を記録する。結果の配列順は選択順を保ち、完了順は別の時刻で表す。

queue時刻を持たない旧recordの待ち時間はnullとし、架空の0を入れない。UTCの時計ずれによる不正な待ち時間もunknown扱いにする。実転送bytesをrcloneから信頼できる形で得られた場合だけbytes/rateを出し、source sizeを送信bytesとみなさない。skip/no-changeと実転送を区別できない場合はその限界を表示する。

preview・status・infoは計測のために転送やstate書き込みを行わない。ログは既存local policyとtoken redactionを維持し、新たな常駐計測serviceや無制限履歴は追加しない。secret/raw認証応答を記録しない。

## 8. 検証と合格条件

本番credential、queue、remote、launchdを使わず、一時workspace・fake-rclone・fixtureで検証する。

| ID | 合格条件 |
| --- | --- |
| C1 | 並列数1/2/4で実測同時数が上限以内。2/4では独立転送が実際に重なる |
| C2 | max-recordsとconcurrencyが独立。未指定件数1と生成側10を混同せず、選択件数を超えない |
| C3 | 不正設定・閉じたgate・不合格reportで起動もqueue/journal更新も起きない |
| C4 | watcher/pollerとexecutorの同時更新、同じpathの新イベント、逆順完了でもrecord消失・重複consumeがない |
| C5 | 同じserviceの二重起動、逆方向の同じpath、manualとautomaticの同時起動で競合転送をしない |
| C6 | upload中の変更、download中のlocal変更、remoteの新世代、echo抑制、除外、manual-reviewを保護する |
| C7 | 失敗と成功の混在、timeout、SIGTERMで未確定recordを保持。自分のchildを回収。異常終了後は安全に再開または保留できる |
| C8 | 旧queue/last-transferを読める。previewは不変。値1への復帰と旧版への停止付き切替をfixtureで確認する |
| C9 | status/info/doctor/help/JSONの設定値と実行実績が一致し、unknown値・secret redactionを正しく扱う |
| C10 | download反映後・journal保存前、およびjournal保存後・consume前で異常終了させ、再起動・復旧後も新イベントとユーザー編集を失わない。保留理由が可視化され、所有child終了を確認できないattemptの解除を拒否する |
| C11 | 更新・切り戻しのfixtureで同一queue/journalの全writer（watcher/poller/executor/manual等）の停止確認を要求し、旧新版writerの混在を許さない |

性能比較は同一の12個以上の独立fixtureを使い、各転送に一定の待ちを持つfake-rcloneで1/2/4を各3回測る。毎回同じ初期queueへ戻し、skipで仕事量を減らさない。中央値で並列2が直列の75%以下、並列4が50%以下を目安とする。実行環境・待ち時間・結果を保存し、閾値未達なら原因を説明して再評価する。これはschedulerの効果の検証であり実回線の速度保証ではない。同時数と保護条件の自動テストは経過時間だけに依存せず、barrier等で実行順を制御する。

実rclone/実回線の性能確認は別の明示的な検証段階とし、専用の小さなデータセット・試験先・実行上限を決めてから行う。既存diffdエラーを解消または試験から切り分けるまで、download性能改善や本番download健全性を完了扱いにしない。fixtureでの実装検証は先行可能。
