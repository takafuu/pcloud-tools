# イベント同期方針（2026-09-23決定）

状態: ユーザーとの本タスク・サイドチャットで確定した変更仕様。実装・配備済みという記録ではない。既存仕様と競合する同期方針は本書を優先する。実装と配備の手順は開発仕様書の既存契約に従う。

## 実装原則

pcloud-managerはrcloneの薄いラッパーとする。[開発仕様書の原則](開発仕様書.md)と[公式機能の照合メモ](rclone機能照合-20260923.md)に従い、既存機能を優先する。bisyncは不採用で固定する。以下は必要な動作を定めるもので、すべてをPythonで自前実装する指示ではない。

## 内容変更

bisyncへ戻さず、イベント駆動方式を維持する。通常はローカルで編集し、クラウドではまれにテキストを編集する。ファイル形式による採用規則の違いは設けない。

同じパスの内容が一致する場合は転送・人の確認を不要とする。内容が異なる場合は更新日時の新しい方を採用する。両側が編集されていても同じ規則とする。同日時で内容が異なる、時刻を取得できない、状態が不明の場合は確認に回す。イベントの受信時刻をファイルの更新日時として代用しない。

更新日時はUTCの同じ秒単位へ揃えて比較する。ローカルの小数秒だけを根拠に新しいと判定しない。同じ秒で内容が異なる場合は確認に回す。サイズ・日時が同じだけでは内容一致と確定せず、必要な対象について共通アルゴリズムの内容ハッシュを比較する。全ファイルのハッシュを常時保存する必要はなく、取得できない場合は不明として扱う。

## 起動・監視再開

常時稼働を基本運用とする。初回・起動時・監視再開時に片側だけに存在するファイルは、停止中の削除だったかを推定せず、新規ファイルとして反対側へコピーする。同じパスに両側のファイルがある場合は内容変更の規則に従う。いずれも既存allowlist/ignore内を対象とする。

起動・監視再開時は、未確定attemptの既存復旧条件を確認したうえで、現在の両側の再照合と停止前の処理待ちの世代整理を先に行い、その後に通常同期を開始する。再照合で復活対象としたファイルへ停止前の古い削除依頼をそのまま適用しない。再照合中に新しく発生したイベントは保持し、古い依頼と区別する。

停止中に削除したファイルが起動時に復活することは許容する。停止中の新規作成と削除を区別するための台帳・tombstoneは設けない。この規則は、以前の「起動時に削除済み状態を判別して復活を防ぐ」という案を上書きする。

## 稼働中の削除

ローカル削除時、同じ対象に未反映のクラウド編集がなければ、pCloud上で通常削除する。pcloud-manager独自のクラウド退避フォルダへ移す案は取り消し、復元はpCloud標準のゴミ箱・Rewindに任せる。この処理ではゴミ箱を空にする `rclone cleanup` を使用しない。[rclone公式pCloud backendの削除仕様](https://rclone.org/pcloud/#deleting-files)と[pCloud Trash API仕様](https://docs.pcloud.com/methods/trash/)を参照。

クラウド削除時、ローカルに未反映の編集がなければ、ローカル版を復元可能な場所へ退避して反映する。クラウド側を標準ゴミ箱へ変更しても、このローカル退避は維持する。

削除と反対側の未反映編集が衝突する場合は、削除イベントが新しくても自動反映せず確認に回し、編集されたファイルを残す。これは両方向に適用する。例: 両側一致後、ローカルを10:00に編集し、クラウドで10:05に削除した場合は、ローカルを保持して確認待ちとする。

稼働中の削除イベントと反対側の未反映編集の衝突を判定するため、最終同期時の更新日時・サイズ等の最小限のメタデータを必要に応じて保持する。これは停止中の削除を推定する台帳ではない。全ファイルの内容ハッシュを常時保存することを通常判定の前提としない。稼働中の削除について、メタデータだけでは未反映編集の有無を断定できない場合は保留する。

ユーザーが確認したpCloud Familyのアカウント画面では、Rewindのアカウント履歴は最大60日と表示されている。アップロード成功済みの版についてはその履歴を安全網とする。未アップロードのローカル編集はクラウド履歴から復元できないため、削除との衝突時に保持する方針は維持する。

## 改名・移動

ローカル監視はfswatchのパス出力からPython watchdogのmacOS FSEvents監視へ切り替える方向とする。ただし、fswatch 1.22.0でもflagsとfile IDを取得できることが確認できたため、移行を能力不足だけで正当化しない。[監視機能の照合](FSEvents監視機能照合-20260923.md)に基づき、旧・新パスの対応付けと欠落対応を最小限の自前処理で満たせる構成を選ぶ。旧・新パスの対応が確定したローカル改名・同一ボリューム移動は、rclone movetoで対応するクラウドパスへ反映する。移動先に同名クラウドファイルが存在しても、ユーザー承認済みの方針としてローカル移動を優先して上書きする。改名ではmtimeが変わらないため、内容変更の日時比較は移動操作の優先順位には適用しない。

編集と改名は別イベントとして扱い、両方の効果を反映する。後続の改名によって未反映の編集イベントを捨てない。処理前にパスが変わっていても同じ対象への編集を移動先へ引き継げるよう、イベント間の対応と依存順序を保持する。

対応付けできない移動は削除と新規作成として扱い、それぞれの規則に従う。別ボリュームかどうかだけで同期方針を変えない。削除・移動と確定できないケースは保留する。既存allowlist/ignoreを維持し、同期範囲を拡張しない。

技術確認: フォルダを対象にするrclone movetoはmoveと同じフィルタ機能を利用でき、--exclude / --exclude-from / --filter-from等に対応する。フィルタ付きでは対象ファイルごとに移動し、除外ファイルは元に残る。可能な場合は各ファイルをサーバー側で移動するため、フィルタの使用が直ちにダウンロード・再アップロードを意味するわけではない。現在のmanager ignoreはファイル名・パス・ディレクトリ規則と例外許可を含むため、rcloneと規則の解釈・基準パスが一致するよう変換するか、事前検証済みの対象一覧を渡す。単一ファイルの明示指定にもCLI側でscope検証を行う。参照: [moveto](https://rclone.org/commands/rclone_moveto/)・[move](https://rclone.org/commands/rclone_move/)。

2026-09-23のローカル一時fixtureでは、rclone v1.75.1のmovetoに.DS_Storeとnode_modules/**の除外を付け、通常ファイルだけが移動し、除外ファイルが元に残ることを確認した。pCloud上の移動試験は行っていない。同期範囲の境界をまたぐ移動の扱いは、この技術確認だけでは確定しない。

## イベント・転送・復旧

pCloud /diffを維持し、diffid、イベント時刻、metadataの更新日時・サイズ・file IDを適切に保持する。通知欠落・overflow・再起動後の不整合時はallowlist内を再照合する。起動・監視再開時の片側のみのファイルは前記の起動規則に従ってコピーし、削除・移動とは推定しない。稼働中に削除・移動として扱う根拠が不足するケースは保留する。

自己発行したクラウド・ローカル通知はorigin/suppression journal等で識別し、同期ループと不要な確認表示を防ぐ。自分がアップロードしたパスという理由だけで後続の他端末編集を無視しない。

通常のアップロード・ダウンロードは方向別にrclone copy --files-from0 --no-traverseへまとめる方向とする。files-from0へ渡す前に既存allowlist/ignoreを検証する。ダウンロードのstaging、退避、世代確認、attempt journal、復旧契約を維持する。部分失敗では成功を検証できた項目だけを完了扱いとし、未確認項目を残す。

## 実装境界

判定と永続状態はCLIが所有し、xbarと専用画面は表示・操作に限定する。通常変更の一件ずつの採用操作を不要にし、判断できないケースを確認画面へ残す。既存のmanualモードから新しい運用への切替は、実装検証と配備時に明示的に扱う。本書を保存しただけで本番設定や同期を変更しない。
