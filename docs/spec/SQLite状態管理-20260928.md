# SQLite状態管理（0.4.0）

## 保存方式

`state_dir/sync-state.sqlite3` が移行後の同期状態の正本。照合済みの版・確認待ち・書き込み待ちはパスごとの行、照合残件は順序付きの行、イベントキューは世代ID付きの行、転送履歴はattemptごとの行に分ける。キューと残件の件数は同一トランザクション内のtriggerで更新する。転送開始・child終了・復旧判定では対象attemptだけを読む。完了履歴は保持するが通常tickでは展開しない。

LaunchAgentで呼ぶ処理は標準ライブラリのみとする既存契約に合わせ、SQLAlchemyではなくPython標準`sqlite3`を使用する。SQL値はパラメーターで渡し、接続キャッシュは4MiB、busy timeoutは30秒。ネットワーク転送中にDBトランザクションを保持しない。writer lifetime・tick lock・cutover barrierは継続する。

## 差分照合

通常tickはイベントと確認待ちから処理対象のパスを選び、そのバッチの記録だけ読む。全treeの名前列挙は初回、監視の開始・再開・欠落など明示的な再照合依頼、directory/moveの展開に限定する。既存の初回照合残件はそのまま引き継ぐ。

ローカルhashはsize、mtime_ns、ctime_ns、inode、device、存在状態がすべて一致するときだけ再利用する。変更後は再計算する。通常tickのクラウドhashは、当該パスのクラウドイベントがなく、ID・size・modified・second・存在状態が一致する保存版に限り再利用する。クラウドイベントがあるパス、初回・復旧照合、手動採用、転送前後、削除直前は最新hashで確認する。クラウド通知がまだ届いていない変更は後続イベントで照合し、転送・削除の直前確認では保存hashを信用しない。

[rclone lsjson公式仕様](https://rclone.org/commands/rclone_lsjson/)と導入版helpで`--hash`省略時のhash未取得を確認した。独自のクラウド転送・hash APIは追加せず既存rclone adapterを利用する。

## 状態表示

`status --detail --json` は保存済みの小さな集計、キュー件数、未完了attempt、実行lock、`event-sync/operation.json`、`event-sync/progress.json`を参照する。照合済み版や完了履歴を全件展開しない。集計は照合結果と同じトランザクションで保存し、同期範囲の設定が変わった場合は古い確認待ち件数を現在値として出さない。

progressには対象列挙・差分照合・upload・download・転送結果検証・batch完了・失敗の段階と更新時刻を保存する。照合中は25件ごとに更新する。転送中の時刻は最後の段階更新時刻であり、継続的な通信や個々の転送完了を保証するheartbeatではない。xbarはCLIの小さな状態キャッシュを描画する。executorが止まっている場合は前回の段階と明示する。

## 移行・復旧

`pcloud-manager state info --json` は保存先と移行元サイズを表示する。`state migrate --json` はpreview。`state migrate --execute --json` は全writer停止・child回収後だけ実行する。実行中tick、writer lease、未完了attemptがある場合は拒否する。`state doctor --json` はschemaとSQLite quick_checkを検証する。既存doctorにもDB検査を追加する。

移行は本番state内の`migrations/sqlite-<日時>-<ID>/`へ元JSONをコピーし、SHA-256一致を確認してから進める。JSONは項目単位で読み、一時DBのトランザクションに格納する。メモリ上限は全ファイルの合計ではなく、個々のJSON項目の大きさに依存する。全入力の正常終了、DB整合性、移行中の元ファイル不変を確認してからrenameで有効化する。元のパスは旧runtimeが誤って使わないためのguard情報に置き換える。バックアップは自動削除しない。新runtimeは有効DBを優先し、破損時に古いJSONへ自動fallbackしない。

旧runtimeへ戻す場合は全writerを止める。SQLite移行後に新しい同期を一度も実行していない場合に限り、保存した旧wheelと検証済みJSONを組で戻せる。稼働後の古いJSON復元は新しいキューや進捗を失うので禁止する。稼働後の切戻しには現在のDBを保持した修正版か、別途検証したexportが必要。

開発は既存fixtureのみを使用し、本番credential/queueを開発workspaceへコピーしない。release wheel・本番state backup・batch drain・全writer停止・移行・4サービス復帰という配備境界を維持する。

## 検証

合成fixtureの30万件baseline・30万件残件・16万件queue（JSON計251MiB）で、旧JSON状態読込のpeak RSSは1304.7MiB、SQLite件数取得は24.2MiBだった。JSON取得1回は2.621秒、SQLite取得30回合計は0.012秒、キュー1000件追加は1.087秒、移行は13.142秒。保存処理を分離したベンチマークであり、同期全体のメモリ保証やネットワーク性能ではない。再現入口はrepo基準`scripts/benchmark-state-storage.py`。

状態移行・中断拒否・イベント世代保持・転送の直前再確認・hash再利用条件・トランザクションrollback・破損時の非正常表示をfixtureで検証する。旧形式の管理用一覧や初回の名前列挙には全対象を扱う入口が残るが、通常の追加・照合・状態表示では詳細全件のJSON展開をしない。

## 本番反映の確認（2026-09-28）

0.4.0 wheelを非editable runtimeへ導入し、本番stateをSQLiteへ移行した。移行時の照合残件283,500件、pushd queue1,000件、diffd queue172,109件を保持し、DB quick_checkは正常。設定とLaunchAgentのhash不変、4サービス復帰、保存gateの受理、APIイベント追加と新しいupload開始を確認した。検証と本番state backupのreceiptは本番stateのrelease/migration記録に保持する。全件照合完了は意味しない。

本番のstatus取得は0.352秒・peak RSS35.5MiB。復帰後15秒間の観測最大RSSはwatcher35.2MiB、executor50.5MiB、API poller133.1MiBだった。以前のAPI poller約4.4GiB・executor約924MiBと比べ大きく減ったが、異なる時点の観測であり全負荷での上限保証ではない。全体回帰413件、後続変更の関連テスト50件、xbar menu/cache10件が通過した。

## xbarの利用者向け表示（2026-09-28）

xbarは先頭で現在の工程を文章で説明し、今回の対象・保存済みの全体照合残件・必要な対応を分けて表示する。背景収集時に連続する小さなsnapshotを比較し、保存時刻が進んだ残件数の減少だけを進捗の根拠として1件保持する。残件が同じ間は観測時刻を更新せず、増加や状態の切替・欠落時に記録を破棄する。工程時刻やキュー件数を進捗とみなさない。転送・検証中の細かな完了件数は未取得と明示し、時刻だけで停止判定しない。古いcacheは前回取得として表示し、対応不要を断定しない。正常cacheに出ていた `status update pending` の既定表示を修正した。本体の同期処理・SQLite schemaは変更していない。
