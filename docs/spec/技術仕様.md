## 確認待ちと診断を分ける（0.5.1）

イベント同期の `manual list` は `records` を採用可能なファイルに限定し、`rechecks` に情報再確認、`diagnostics` に処理エラーと構造上の問題を返す。`count` と `review_count` は採用判断の件数で、`recheck_count` と `diagnostic_count` を別に集計する。画面は診断欄に選択操作を置かない。保存情報に両側の存在状態がなく、採用可能と確認できない旧recordも診断へ分類する。表示取得はクラウドへの通信を行わず、採用previewは最新の版とイベント世代を引き続き検証する。

通常ファイルとして登録されたローカルフォルダは、既存rclone列挙で範囲内の子ファイルを抽出し、syncイベントを永続化してから元の保留と取得済み世代を解除する。子ファイルの片側欠落をフォルダ通知だけで削除とはみなさない。列挙失敗、ファイルとの衝突、フォルダの変化ではイベントを保持する。再照合中も既存のファイル枠内で旧フォルダ保留を最大10件ずつ取り出す。同期範囲、資格情報、SQLite schemaは変更しない。

## 双方向同期の競合方針（0.5.0）

この方針は、以前の「同時刻の異なる内容や削除・編集の競合を人の確認待ちにする」動作を置き換える。通常の更新はファイルの更新日時が新しい方を採用し、両側を揃える。同期実行時刻を比較に使わず、コピーで元の更新日時を保持する。比較精度は従来どおり秒単位で、同じ秒なら設定した側を採用する。時計ずれや日時を保持したコピーと実際の編集順の違いは運用上許容する。

両側の変更が衝突した場合と、同時刻で内容が違う場合は、不採用版をローカルcore直下の `.conflict/` へ退避する。確認済みの削除イベントと編集が衝突した場合は、編集版を退避して通常の場所では削除を採用する。通信失敗や情報未取得は削除とみなさない。情報の取得に成功したことと、対象イベントの世代確認が前提となる。

退避が失敗しても同期・上書き・削除を続行する。失敗はstate直下の `conflict-archive-failures.jsonl` と当該実行結果に記録する。ただし退避中に元のファイルやイベントが変わった場合は、古い判断で上書きせず、そのファイルだけ次の再評価へ回す。他の対象は進める。

設定は既存config dirの `.env` に記載する。場所は `pcloud-manager info` で確認できる。

| キー | 初期値 | 意味 |
| --- | --- | --- |
| `PCLOUD_TOOLS_CONFLICT_SAME_TIME` | `local` | 同時刻の採用側。`local` または `cloud` |
| `PCLOUD_TOOLS_CONFLICT_RETENTION_DAYS` | `14` | 退避の保持日数。非負整数 |
| `PCLOUD_TOOLS_CONFLICT_MAX_BYTES` | `100000000000` | 退避内容の合計容量上限。非負整数、十進の100GB |

期間超過分を削除し、容量超過時は古い退避から削除する。新規退避前に予定サイズ分の空きを確保する。単体で容量上限を超えるファイルは退避を省略し、失敗を記録して同期を続ける。管理対象はこの機能が作成した退避で、上限は内容の容量を対象とする。索引やメタデータの容量は含めない。保持処理は同期実行時と退避作成時に行い、停止中は次回実行まで遅れる。

退避はUUIDのディレクトリごとに、元の相対パスを保った `data/` と `record.json` を保存する。`.conflict/` は通常の同期・監視・全件列挙から除外する。索引はstate直下の `conflict-archive.sqlite3` に保存する。launchdの標準ライブラリ運用を維持するため、既存状態DBと同様に標準のsqlite3とパラメータ化したSQLを使う。既存同期DBのschemaは変更しない。

退避一覧は `pcloud-manager diffd transfer manual archives --json`、Finderで開く場合は同コマンドに `--open` を付ける。xbarにも「退避した競合版を開く」を用意する。録画など書込み継続中のファイルについては新しい運用を確定していないため、今回の変更では既存の書込み安定待ち設定を維持する。


## 独立した再確認と日時優先（0.4.4）

同期と再確認を独立した実行枠で並行処理する。既存の自動実行入口で再確認workerを別threadとして開始し、転送lockとは別の専用lockで重複起動を防ぐ。再確認は1回最大100件、同時1workerで、同期の100件枠を消費しない。既存2つの定期実行入口の片方が転送中でも、もう片方から再確認を開始できる。通信とディスクは共有する。

確認中はDBトランザクションを保持しない。結果反映時だけ短い書込みtransactionを使い、対象のreview・baseline・両側イベント列・ローカルstatを確認開始時と比較する。変化があれば結果を破棄して後で再確認する。workerはファイルの転送・削除やbaseline更新を行わない。完全一致する古い通知だけを整理し、同期が必要な項目は新しいイベント世代として通常同期へ戻す。通常同期のreview保存も世代を比較し、workerの結果を古いcacheで上書きしない。

両側にファイルがあり更新日時で判断できれば、新しい方を自動採用する。クラウドIDの変化だけでは保留しない。同じ内容なら転送不要。同じ秒の異なる内容、日時不明、削除と変更の競合、情報取得失敗は別途扱う。

「情報を再確認」は独立workerへ再確認を依頼する。「一覧を更新」で結果を表示する。CLIは `pcloud-manager diffd transfer manual recheck --execute`。単発実行は `pcloud-manager diffd transfer manual recheck-run --execute --max-records 100` で、`--execute` なしはpreview。xbarでは同期工程と別に、再確認の稼働状態・今回の件数・残件・更新時刻を表示する。失敗時はイベントを保持して次の定期実行で再試行する。

両workerとも既存writer leaseを使う。SQLite schema変更やLaunchAgentの追加はない。実装はrepo root基準の `src/pcloud_tools/review_worker.py`、`sqlite_state.py`、`event_sync.py`。ローカルstatが検証済みbaselineと同じなら保存済みハッシュを再利用する。


## 再照合中の通常同期（0.4.2）

SQLite使用時は、再照合中にも追加・変更イベントを処理する。通常ファイルの比較・転送対象を1バッチ最大100件（呼出側のmax_recordsが小さければその値）に抑え、最大半分をイベント優先枠、残りを保存済みの照合残件へ割り当てる。イベントがなければ照合で枠を使う。max_records=1ではイベントと照合を交互に処理する。directoryや移動の検証・展開は別途必要になる。転送自体を途中で割り込ませる方式ではないため、反映は進行中バッチの完了と書込み安定待ちの後になり、大きいファイルや通信遅延では時間がかかる。

イベント枠はローカルとクラウドへ分配し、それぞれ新しい項目と古い項目を抽出する。同じイベントIDの確認保留は優先枠を占有させず、新世代が届けば再び対象にする。各抽出の走査行数も制限する。照合対象パスにイベントがあれば通常の変更・削除判断を適用し、単なる片側欠落として復元しない。照合中に新世代が届いた場合は後のバッチへ回し、保存した世代以外を消費しない。移動・directoryイベントは既存の検証・展開処理を先に使う。背景照合の終了や再起動で優先対象を消さない。

SQLiteのローカル待機キューは旧JSON用件数上限で新しいイベントを落とさず、行単位で保持する。処理・表示の読み取り量は引き続き限定し、同じパス・操作の世代置換規則を維持する。旧JSON形式のoverflow時再照合動作は変更しない。配備前に既に記録できなかった変更は、この変更だけでは復元できず、保存された再照合要求による回収対象となる。

再照合ID・残件・既存の一時計測sessionを維持する。SQLiteのschema変更はなく、通常のrelease切替で反映する。実装repo root基準で `event_sync.py` の混在バッチ、`sqlite_state.py` の優先抽出、`event_sync_watch.py` の永続化を確認する（各ファイルは `src/pcloud_tools/` 配下）。


## 今回の再照合だけ時間を記録する（0.4.1）

`pcloud-manager trace start --until-reconciled --execute` は進行中の再照合IDに結び付けて一時計測を開始する。通常時は無効で、再照合の完了・対象の変更・7日経過・16MiB到達で記録を止める。`--execute` を省略するとpreviewのみ。同期や再照合自体の開始・停止・やり直しは行わない。手動停止は `pcloud-manager trace stop --execute`。保存済みログは削除しない。

状態と保存先は `pcloud-manager trace status --json`、集計は `pcloud-manager trace report`、診断は `pcloud-manager trace doctor --json`。`help trace`・`help --ai "同期の時間を調べる" --topic trace`・`info paths` から再発見できる。保存先は既存state配下の `diagnostics/sync-trace/`。sessionごとにJSONLを分離し、directory0700・log0600で保存する。設定ファイルやLaunchAgentへ恒久的な有効化設定は追加しない。

記録するのは時刻、工程、固定操作名、呼び出し回数、経過時間、Python CPU時間、終了した子processのCPU時間、例外型のみ。ファイル名・コマンド引数・認証情報・stdout/stderr・内容は保存しない。ローカル処理はバッチ内集計で、ファイルごとのログ書込みを避ける。rclone呼び出しは開始と終了、工程は切替、バッチは終了時に記録する。書込み障害は同期を中断させない。

集計は終了したバッチが対象。開始のみ残った操作は中断・実行中の可能性があり、JSONLで確認する。batch・cloud-inventory・rclone等の時間は入れ子なので単純合算しない。経過時間とCPU時間の差には通信・ディスク・ロック・スケジューリング等の待機が含まれ、それだけでネットワーク待ちと断定しない。過去の計測前の処理は復元できない。コードは `src/pcloud_tools/sync_trace.py` と `cli_trace.py`、計測入口は `event_sync.py` と `event_sync_remote.py`（実装repo root基準）。

## 現行イベント同期の表示（0.4.0）

イベント同期の現在の入口は `status --detail --json`。0.3.2ではCLIが `pcloud-event-status.v1` を集約し、xbarはその保存キャッシュを表示する。初回照合の保存残件・確認待ち件数・保存日時と、取得時点のexecutor稼働を区別する。未取得は未取得、古い保存状態は更新待ちとし、全件一致や同期完了を推測しない。確認画面の件数も同じScopeと保存stateから計算し、取得した版の保存時刻を表示する。画面更新でクラウドの走査・ハッシュ取得は行わない。

## 1. 目的

`pcloud-manager` は、この環境の `rclone` / `pCloud` 運用をまとめるPython CLIです。`pcloud-tools` distributionの一部としてwheel化し、正式版はuvの隔離tool environmentから実行します。`/Users/takafumi/p-core/dev/pcloud-tools/` は開発・test・release buildの場所であり、正式版runtimeはこのcheckoutをimportしません。

主な責務は次のとおりです。

- `p-core` と `pcloud:core` の `bisync`
- `vault` / `crypt` の optional mount
- `launchd` による autosync の管理
- `launchd` による `pcloud-pushd` / `pcloud-diffd` の human-gated daemon 起動
- `status` / `doctor` による状態可視化
- sync scope file ベースの同期範囲制御
- stale lock / missing listing など、運用でよく起きる障害の軽減
- pushd/diffd の queue-only / diffid-only 監視を実 upload/download から分離すること

## 開発・本番の実行境界

本番の全入口（CLI、互換wrapper、LaunchAgent）は `/Users/takafumi/bin/pcloud-manager` 等のpublic wrapperから、install済みの非editable wheelへ委譲する。`/Users/takafumi/p-core/dotfiles/.zsh/functions/pcloud-manager` は互換入口としてpublic wrapperを呼ぶだけにし、development `src` / `.venv` を参照しない。開発checkoutの編集を本番へ反映するには、検証済みreleaseの明示的installが必要。

daemon behavior と gate:

- `pcloud-pushd` は sync scope 内のlocal eventをqueueへ追加し、bounded executorがeligible recordをuploadする。resident plistとexecutor plistのwrite/reloadには専用gateとterminal human reviewが必要。
- `pcloud-diffd` はpCloud `/diff` APIをbounded pollし、sync scope内のremote changeをqueueへ追加する。 親フォルダのパス解決はcacheと同じdiff応答内のfolder metadataを使い、不足する祖先だけを`listfolder`で取得する。これにより現在は削除済みのフォルダを含む過去の差分も復元できる。復元できないAPIエラーではresult番号を記録し、cursorと既存queueを保持する。pollingとdownload executorは別serviceで、plistのwrite/reloadには専用gateとterminal human reviewが必要。
- `pushd transfer executor-run` / `diffd transfer executor-run` は dev-state fake-rclone 専用の queue executor tick。pushd queue は transfer 命令ではなく再確認候補として扱う。`pushd executor-run --execute` は local fingerprint (size / mtime_ns) を `state_dir/pushd/upload-candidates.json` に記録し、同じ fingerprint が `PCLOUD_TOOLS_PUSHD_UPLOAD_SETTLE_SECONDS` (production default 30 秒) 続いた record だけ upload する。executor tick 時点で消えた `upload` 候補は、upload成功履歴に関係なく即時かつ通知なしでqueueからpruneする。以前uploadしたpathに対する明示的な`delete` / `rename` recordだけmanual reviewに残し、status JSONに対象詳細を含め、xbarのreview actionからtransfer previewをTerminalで開く。`--execute --consume-on-success` で fake transfer と successful record consume まで行う。
- `pushd launchd executor-plist` / `diffd launchd executor-plist` は dev-state fake-rclone queue executor 用の StartInterval LaunchAgent plist surface。`.dev-state/launchd/com.example.pcloud-*-executor.dev.plist` だけを書ける。public LaunchAgent write、`launchctl`、real transfer automation は行わない。
- `pushd transfer automation-gate` / `diffd transfer automation-gate` は public real-transfer queue executor automation の read-only gate。予定 public executor label/plist/StartInterval と automation command readiness を表示し、reviewer/operator approval が揃うまで public plist write、`launchctl`、automatic real transfer は行わない。
- `pushd transfer automation-run` / `diffd transfer automation-run` は gated automatic real-transfer executor tick。real-transfer gate、automation gate、automation-run gate、saved shadow validation report、non-`fake-rclone` rclone、`--execute`、`--consume-on-success`が揃うまで拒否する。manual-review record は転送対象から除外・保持し、eligible transferを阻害せず、それ自体ではerror終了やchat通知を起こさない。`pushd automation-run --execute` は gate が揃った tick 冒頭で missing-local startup cleanup を行ってから plan を組む。直接CLIの未指定時は `--max-records 1` で one transfer record per tick だけ実行/consumeし、生成側のpublic automation payloadは既定10件とする。失敗/不明/deferred record は保持し、automation launchd review は multi-record plan でも confirmed selected target 1 件を current bounded automation tick として approve できる。
- transfer executorはserviceごとに1〜4件のbounded concurrency（既定1）を使い、`--max-records`の選択件数上限とは独立している。queue/journalのread-modify-writeは共通process lock、同一pathは方向をまたぐpath lock、同一serviceのtickはtick lockで保護する。常駐watcher・API poller・executorなどの長寿命writerはservice lifetime sessionを保持し、切替・切り戻しは全writer停止とchild終了確認の後にcutover sessionを取得して行う。last-transferにはperformance schema version、resolved/peak concurrency、batch elapsed、選択/開始/成功/失敗/timeout/deferred/conflict件数とrecord時刻を保存する。
- queue recordの追加識別子`event_id`がある場合は選択世代だけをconsumeし、同じpathの新世代を保持する。旧queue形式は読み続け、event_idのない旧recordは実行可能なtickでlock下に識別子を補ってから選択世代の一致を確認する。previewはstateを書かない。downloadは一意なstagingからdestination fingerprintを再確認して反映し、競合時はconflict copyとmanual-reviewを残す。
- `transfer recovery preview` は未確定attemptを表示し、`transfer recovery run --execute --attempt-id <id>` はchild終了、全writer停止、最新event_id再確認、local fingerprint再確認を明示的に要求する。解放は最新候補の再評価だけを行い、成功receiptの捏造やqueue consumeは行わない。
- 未確定attemptがある間はexecutorのselection・child start・consumeを拒否する。解放後のdownload再評価はattemptに保存したevent_idと元の転送前fingerprintを参照し、local変更を検出した場合はconflict/manual-reviewへ送りdestinationを上書きしない。
- `pushd launchd automation-plist` / `diffd launchd automation-plist` と `automation-reload` は public real-transfer queue executor LaunchAgent write / reload gate。terminal-reviewed flags と service-specific plist/reload gate が揃うまで、public plist write、`launchctl`、automatic real transfer は行わない。直接CLIのexecutor tickは未指定時に `--max-records 1` を使うが、生成側のoperational public executor plistは既定10件で、`--max-records` の正の整数を受け付ける。
- transfer plan は sync scope/default-exclude 判定後に hidden path component を excluded/skipped にする。macOS screenshot などの transient dotfile は automatic transfer command に出さない。
- `pushd queue prune-excluded` は excluded queue record だけを remove する cleanup surface。preview は read-only。dev `--execute` は dev-state guard、public `--execute` は `--reviewer-approved-excluded-record-cleanup` と `PCLOUD_TOOLS_PUSHD_QUEUE_PRUNE_EXCLUDED_GATE=operator-approved-pushd-queue-prune-excluded-v1` が必要。
- serviceの登録・実行状態は文書へ記録せず、`pcloud-manager pushd status --json`、`pcloud-manager diffd status --json`、各`launchd status`で確認する。

The prior last-transfer payload must have `mode: real-rclone-transfer`, match the service and direction, include at least one successful result, and include no failed or timed-out results. This evidence affects only the read-only automation/plist gate review and does not run transfers or launchctl.
- The public automation launchd surfaces (`pushd|diffd launchd automation-plist` and `automation-reload`) are guarded write/reload paths. `automation-plist --execute` can write only the service-specific public executor LaunchAgent plist after terminal review flags, saved shadow report, automation gate review, public wrapper check, service-specific plist gate env, and public non-dev runtime pass. The generated public executor payload defaults to `--max-records 10`, and the operational check accepts any positive integer; this is separate from the direct CLI default of 1. `automation-reload --execute` can run only service-specific `bootout -> bootstrap` after an operational automation plist, launchctl, terminal review/rollback flags, and service-specific reload gate env pass.
- `pushd queue prune-excluded` previews and, after a dedicated cleanup gate, removes only queue records currently classified as excluded. This is intended for hidden/transient dotfile queue records and does not remove planned upload records, invalid records, files, remotes, or listing cache data.
- `pushd transfer recovery run` and `diffd transfer recovery run` require `--execute --attempt-id <id> --child-exit-confirmed --writers-stopped --latest-event-ids-rechecked --local-fingerprints-rechecked`. These four confirmations follow all-writer stop and child exit checks; recovery only releases an attempt for fresh candidate evaluation and never consumes queue records.
- `scripts/pcloud-shadow-validation.py` creates a temporary workspace, runs preview/manual/dry-run/gate/fixture-parser/action checks, confirms unsafe state dirs are refused, and deletes the temp workspace at process exit.
- `scripts/pcloud-shadow-validation.py --report-path <path>` writes the same structured JSON report to disk for operator/reviewer records.
- The transfer layer remains preview/dev-fake-rclone-test only unless the separate real-transfer gate is explicitly opened. Pushd and diffd automatic transfer execution paths and their gates are implemented; whether either service is enabled, loaded, or healthy is determined by its runtime status and gate reports. Normal sync/resync and listing cache operations remain separate gates.

validation report schema:

- `schema_version`: currently `pcloud-tools-shadow-validation.v1`
- `status`: `ok` only when all checks passed; otherwise `error`
- `workspace`: script-created temporary `pcloud-shadow-validation-* / workspace` path
- `state_dir`: exactly `workspace/.dev-state/state`
- `checks[]`: records with `name`, `status`, and `detail`

validation gate rules:

- An acceptable validation report requires exit code 0, top-level `status: ok`, every `checks[].status == ok`, `workspace` under the script-created temporary `pcloud-shadow-validation-*` directory, and `state_dir == workspace/.dev-state/state`.
- The report must include at least `pushd dry-run state`, `diffd dry-run state`, `pushd gate closed`, `diffd gate closed`, `pushd fswatch fixture planned uploads`, `pushd fswatch probe gate closed`, `diffd diff fixture planned downloads`, `diffd api-poll gate closed`, `pushd launchd resident plist write gated`, `pushd launchd reload fake launchctl state`, `diffd launchd operational plist write gated`, `diffd launchd reload fake launchctl state`, `pushd transfer gate closed`, `diffd transfer gate closed`, `pushd transfer checklist read-only`, `diffd transfer checklist read-only`, `pushd transfer consume read-only`, `diffd transfer consume read-only`, `pushd transfer consume guarded run`, `diffd transfer consume guarded run`, `fake-rclone transfer calls`, `pushd queue not consumed`, `diffd changes not consumed`, `unsafe state dir guard`, `temporary workspace guard`, and `temporary state dir guard`.
- A failed gate blocks any new public launchd change, fswatch/API daemon expansion, transfer execution, sync/resync migration, and old monolith legacy archive.
- Rollback for public launchd changes means using the reported rollback commands only after operator review; do not run `bootout`/`disable` opportunistically from tests.
- Current command behavior, safety gates, and verification procedures are defined by this specification, `利用ガイド.md`, and command help.

## 5. Sync モデル

### 5.1 基本方式

`sync` は `rclone bisync` を使って:

- Path1: `local:/Users/takafumi/p-core`
- Path2: `pcloud:core`

を同期します。

共通オプション:

- `--conflict-resolve newer`
- `--resilient`
- `--skip-links`

### 5.2 scope 制御

通常の `sync` / `autosync` は sync scope file ベースです。

sync scope file:

- `/Users/takafumi/p-core/.pcloud-sync-allowlist`

filter output:

- `~/.pcloud/bisync.filter`

重要:

- 実際の同期範囲は README の方針文よりも sync scope file の内容が優先されます。
- `.pcloud-sync-allowlist` の `/` は configured core root 全体を表します。危険物・生成物・秘密情報は `.pcloudmanagerignore` と generated rclone filter で除外します。

### 5.3 mode

sync mode は内部的に次の種類です。

- `normal`
- `autosync`
- `resync`
- `full-resync`
- `track-renames`

意味:

- `normal`: sync scope 付き通常 bisync
- `autosync`: launchd watchdog から起動される sync scope 付き通常 bisync
- `resync`: sync scope 付きで bisync state を作り直す
- `full-resync`: sync scope filter を外した one-shot full-tree resync
- `track-renames`: rename tracking 付きの foreground sync

### 5.4 scope guard

sync scope と full-tree scope を行き来すると bisync state の前提が変わるため、`last-resync-scope` を `~/.pcloud/last-resync-scope` に記録します。

ルール:

- 通常 sync の前に前回の resync scope と今回の scope を比較する
- scope が変わっていたら通常 sync は拒否する
- 対応する `resync` が成功したときだけ baseline を更新する

## 古いdownload依頼の自動除外と状態計算

rclone downloadがexit 3/4を返し、stderrにsource側の不在診断が明示され、child終了が確認された場合、選択path/event_idと一致するdownload recordだけを自動除外する。終了codeだけでは判定しない（[rclone exit code](https://rclone.org/docs/#exit-code)）。destination不在、認証・network失敗、timeout、child終了不明は除外せず保持する。local内容、別event_id、cursorは変更しない。不在はperformance.obsoleteへ計上し、succeeded/failed/manual_review/conflictには数えず、元returncodeとstderrは実行記録へ残す。ユーザー操作や通知は求めない。

v0.2.2で付与したdownload_reviewは、reason=remote-source-missing、returncode=3/4、現行event_id一致、download actionという条件が揃うものだけ次のadmitted automation tickで除外する。証跡は本番stateのobsolete-download-cleanup.jsonへ保存する。通常の実行gate・report・consume条件に加えtick lock/writer lifetimeを取得し、未確定attemptがないことを再確認してから変更する。preview/statusやgate未充足時には清掃しない。review preview/retryは旧marker用の互換入口として残す。

[API /diff](https://docs.pcloud.com/methods/general/diff.html)のmetadata.fileidをremote_file_idとして保持し、同一file IDの複数観測は最大diffidの最新名/actionへ集約する。API pollのqueue追加時も同一file IDかつ同じか古いdiffidだけを一つのqueue lock内で置換する。古い応答のreplayは新しい観測を置換しない。file IDを得られない旧recordの名前を推測して消さない。file ID付きrenameは新名へのdownloadとして扱うが、localの旧名ファイルの削除・renameは行わない。IDのないrenameや実ファイルへのdelete・競合は従来の確認待ちを維持する。

実装はdownload_review.py、diffd_events.py、service_daemon_plan.py、cli_service_daemon/__init__.py。executorはtick lockとwriter lifetime sessionを獲得してからevent ID補完・attempt生成を行う。statusはexecutor lockがactiveな間の未完了attemptを復旧警告にしない。停止後も残るattemptは従来どおり復旧対象として表示する。

状態計算は各planの入口でsuppression/upload-origin journalとignore ruleを1回読み、そのplan内で共有する。次planで読み直し、local fingerprintは現在値を確認する。UI用cacheと最上部「要操作」は別project pcloud-statusが所有する。

## 個別競合解消契約（0.2.4）

repository root基準の `src/pcloud_tools/conflict_resolution.py` と `cli_conflict.py` が実装です。preview tokenはpath・strategy・core/state/remote識別・両側の対象レコード全field・local SHA-256/stat・remote ID/mtime/size/hashから生成します。applyで再検証し、両版の私有バックアップとhashを検証後、短い両queue lock下で世代とlocal hashを再確認します。ネットワーク待ち中はqueue lockを持ちません。両serviceのtick lock・writer session・path lockでexecutorやruntime切替と排他します。

local採用ではdiffd remote-changesだけ、cloud/both採用ではpushd queueだけをatomic replaceします。無関係なrecord・未知field・cursor・元ファイル・remoteを保持します。bothは別名をexclusive createし、そのupload追加と元push除去を1回のqueue commitで行います。commit前の中断は元の競合を残し、commit後は選択済みqueueを残します。失敗時にはprepared receiptや別名コピーが残り得るため、再操作前に一覧とreceiptを確認します。以後のremote書込みは通常のgated executorが担当し、確認時点より後のremoteをロックするものではありません。

バックアップrootは0700、退避内容とreceiptは0600。privateなデータは公開repositoryに記録しません。削除/移動・不在・symlink・旧pendingを推測で解消しません。


## 手動で選択するクラウド取り込み（0.2.5）

`PCLOUD_TOOLS_DIFFD_DOWNLOAD_MODE=manual` は自動download executorを転送・queue消費なしで終了させる。API pollerは変更検出を続け、xbarにクラウド変更件数を表示する。互換既定値は `auto`。自動pushは継続するが、検出済みの同じパスのcloud変更は従来の競合保留対象となる。検出前の変更まで保護する保証はない。

xbarの「クラウド変更」からTerminalでファイル番号を選び、サイズと更新日時を見て、クラウド版を取り込む・ローカル版を採用する・保留から選ぶ。CLIは `diffd transfer manual list --json`、`preview --path PATH --choice pull|local --json`、`apply --path PATH --choice pull|local --token TOKEN --execute`。preview tokenはパス・設定・両側の内容・queue世代に結び付く。確認後に変化した場合は再確認が必要。

明示的な採用前に両版をstate配下の `manual-pulls/` に退避する。pullは一時ファイルから置換し、取り込みの再uploadを抑止する。localはuploadを予約する。元からローカルにないファイルでlocalを選ぶこと、delete/rename、symlink、scope外はこの入口では扱わない。保留・取消では転送しない。失敗時はreceiptと未確定attemptを保持して自動再試行せず復旧対象とする。退避は自動削除しない。

ファイル移動・改名ではmtimeだけで同一ファイルと判断しない。移動先の内容とcloud保存を確認して旧パスを別途整理する。cloudだけにあるファイルを自動pullで復活させない。同期除外のdirectoryを変更するときは既存queueにも同じscopeを適用する。

## 一括JSON処理（0.2.6）

`diffd transfer manual batch preview|apply --input PATH|- --json` はGUIと外部プログラムで共用する入口。入力は `{"schema":"pcloud-manual-batch.v1","items":[{"path":"Documents/example.txt","choice":"pull"}]}`。choiceはpull/local/hold。入力は最大16 MiB・10,000件で、同一パスの重複を拒否する。

previewは各項目の最新の両版情報とtokenを返す。applyはその出力全体、またはdetailsを入力にし、`--execute` を指定する。全項目の形式とtokenの有無を実行前に検証し、内容・世代の再照合と退避は既存の個別manual処理に委譲する。選択時点から変更された項目は失敗する。holdは同期状態を変更しない。

結果はitemsとcountsで返す。状態はready/held/completed/upload-queued/failed/unprocessed。applyは最初の失敗で停止し、後続を未処理にする。既に成功した項目は巻き戻さない。途中失敗を含むreportはstatus=error・非0終了とし、自動再試行しない。`--progress-jsonl` を付けるとstderrに項目開始・終了のJSONを出し、stdoutは最後のreport一つに保つ。バッチ全体の永続記録は追加せず、退避・復旧記録は各項目の既存manual-pullsに残す。

## 古いクラウド情報の再確認（0.4.3）

確認画面の「情報を再確認」、または `pcloud-manager diffd transfer manual recheck --execute` で再確認を依頼する。`--execute` なしはプレビュー。依頼は同期処理の区切りで処理されるため、直ちに完了するとは限らない。「一覧を更新」で結果を確認する。情報未確認の項目と、採用する版を選べる項目を区別し、取得失敗を含む一括確認では反映へ進めない。

古いファイルIDのイベントは、最新クラウド情報が検証済みbaselineと一致し、ローカル内容も両方と一致する場合だけ自動解除する。ファイルの転送・削除は行わず、取得した世代のイベントのみを消費する。それ以外は現在の両側情報を付けて採用判断へ回し、明示的な採用は最新情報に結び付いたtokenで再検証する。取得失敗ではイベントと保留を保持する。

SQLiteの再照合中は、通常イベント枠の一部（100件バッチなら最大10件）で古いIDの保留を順次再確認する。走査量とcursorを制限し、全件照合や新着同期を占有しない。小さな再確認依頼ファイルを別に保存するため、実行中バッチの状態保存によって依頼が失われない。DB schema・同期範囲・既存計測sessionは変更しない。

### 0.4.5

Review counts are recomputed from committed review rows inside the same short SQLite transaction. A sync batch cannot restore an older count after the independent review worker completes. No database schema change.
