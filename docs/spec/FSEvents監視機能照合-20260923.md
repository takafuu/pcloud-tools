# FSEvents監視機能の照合（2026-09-23）

状態: 公式資料・対象版ソース・一時fixtureによる調査。監視方式の配備変更はしていない。現行fswatch 1.22.0とwatchdog v6.0.0の実装を照合した。オンラインのfswatch manualは1.17.1、watchdog stable APIページは2.1.5表示のため、対象版ソースと導入済みhelpを合わせて確認した。

## 調査結果

fswatchはパスだけでなくイベントflagを出力できる。1.22.0のmacOS FSEvents backendは拡張file IDをイベントのcorrelation値へ渡す。CLIでは%fがflags、%cがcorrelation、%pがpath。これはFSEventsの単調増加event IDとは別のものであり、永続的に一意な処理世代として扱わない。参照: [fswatch 1.22.0 FSEvents実装](https://github.com/emcrisostomo/fswatch/blob/1.22.0/libfswatch/src/libfswatch/c%2B%2B/fsevents_monitor.cpp)。

実装repoのsrc/pcloud_tools/cli_service_daemon/__init__.pyにある_pushd_fswatch_resident_commandは、recursiveとevent-flag-separatorのみを渡し、flagsやcorrelationを出力する指定がない。実機の一時fixtureでも、この現行引数ではパスだけが返ることを確認した。fswatch自体の制約とは区別する。

watchdogのFileMovedEvent/DirMovedEventはsrc_pathとdest_pathを持つ。[v6.0.0 FSEvents実装](https://github.com/gorakhargosh/watchdog/blob/v6.0.0/src/watchdog/observers/fsevents.py)は同じ通知batch内のinodeを使って改名前後を対応付ける。片側しか見つからなければ存在状態から作成/削除へ分け、統合された変更flagも処理する。既製の対応付けを使えばラッパーの自前処理を減らせる。一方、batchをまたぐ連続改名まで常に対応付ける保証とはしない。

FSEventsは操作履歴を一件ずつ完全に届けるAPIではなく、通知が統合される場合がある。編集・改名は内部で別の処理として保持するが、「ユーザー操作2回ならOS通知も必ず2件」という前提にはしない。[Appleの公式ガイド](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html)はMustScanSubDirsでの再走査、UserDropped/KernelDroppedでの監視範囲再走査、RootChangedへの対応を説明している。

fswatchではこれらの一部native flagがPlatformSpecificへまとめられる。watchdogでも通常のFileSystemEventだけで全てのnative障害情報が通知されると仮定しない。採用時はoverflow・監視root変更・監視停止の検知経路を確認し、ライブラリの標準機能で対応できる範囲を先に使う。

## ローカルfixtureの確認

一時directoryにbefore.txtを作り、監視開始後に内容編集とafter.txtへの改名を続けて実行した。現行引数と、fsevents_monitorを指定してformat=%c・%f・%pをprint0で出す引数を比較した。

現行引数ではパスのみ。拡張出力では編集・改名flagを確認し、before.txtとafter.txtに同じ非ゼロcorrelation値が付いた。編集と改名が複数flagとして一つの通知へ統合される例も観測した。これは一つの通常ケースの確認であり、overflow、全ての保存方式、複数ボリューム、再起動の保証を検証したものではない。fixtureと監視childは終了時に片付け、本番ファイル・監視serviceは変更していない。

## 実装へ引き継ぐ条件

- 通知の種類と取得できる識別情報を入口で捨てない。イベント時刻をファイルmtimeとして使わない。
- 編集と改名の両方の効果を保持する。複数flagを最初の一つだけで判定しない。対応付けが不明な操作を推測して破壊的に反映しない。
- fswatchを使う場合、固定の数値・flag部分とパスを明確に分離し、NUL区切りで改行入りファイル名も扱う。現在のstrip・行分割のままでは十分でない。
- FSEventsのlatencyによるbatch化と、ファイルの書き込み完了待ちは別の目的として扱う。不要に即時・一件ずつのrclone起動へ変換しない。
- 欠落時は定めた範囲を再照合し、起動・監視再開時は確定済みの再照合規則を適用する。通常時の全件巡回を追加する前に必要性を確認する。
- 自分が発行した変更は選択版・処理世代で照合する。短時間の全イベント無視やパスだけの恒久抑止はしない。
- watchdog移行の方向は維持して比較するが、「fswatchはパスしか取得できない」を移行理由にしない。標準ライブラリの機能を使って、必要な保証をより少ない自前処理で満たす構成を選ぶ。
