# イベント同期 0.3.2

本書の相対リンクはこの文書のディレクトリを基準にする。[確定方針](イベント同期方針-20260923.md)、[rclone照合](rclone機能照合-20260923.md)、[FSEvents照合](FSEvents監視機能照合-20260923.md)を実装する。0.3.2の仕様であり、配備の完了は別途、導入先のrelease receiptで確認する。

## 設定と処理

既存の `PCLOUD_TOOLS_DIFFD_DOWNLOAD_MODE` に `event` を追加した。`auto` と `manual` は従来の動作を維持し、自動移行しない。設定モジュールの `sync_policy` は `event` のときだけイベント同期を選ぶ。設定を切り替える場合は[開発仕様書](開発仕様書.md)の全writer停止・drain・backup・wheel切替・復帰手順に従う。bisyncは使用しない。同期範囲・allowlist・ignore・実行gateは維持する。

内容が同じなら何もしない。内容が異なる場合はUTCの整数秒で更新日時を比較し、新しい側を採用する。両側編集でも同じ規則を適用する。同じ秒、比較できないハッシュ・日時、状態不明は確認待ちにする。すべてのファイルの過去ハッシュを先に登録する必要はない。処理したファイルについて、最後に双方の一致を検証した版情報をstateに保持する。

起動・監視再開・欠落検出時は未完了attemptの復旧を先に要求し、同期範囲を再照合する。片側だけに存在するファイルはもう片側へコピーする。停止中の削除は復活し得る。削除履歴台帳は持たない。走査開始前のキュー世代だけを保存・整理し、走査中の新イベントを残す。対象リストをstateへ保存し、通常同期に先行してtickごとの件数上限内で処理する。

稼働中の削除は、相手側が最後の同期版から変わっていないと検証できた場合だけ反映する。ローカル削除は `rclone deletefile` を使い、pCloud標準のゴミ箱・Rewindに任せる。独自remote trashへの移動と `cleanup` は行わない。クラウド削除ではローカル原本をstate配下へ退避・検証してから削除する。相手側の未反映編集や不明状態があれば保留する。

## 監視と転送の分担

fswatch 1.22のFSEvents monitorを利用し、file ID・flags・pathをNUL区切りで受け取る。`%c` はinodeに基づくfile IDであり、永続的なFSEvents event IDではない。watchdogも照合したが、今回必要な欠落通知とrich event情報を既存fswatchから取得できるため依存を追加しない。

同じbatchのfile ID、旧名の不在、新名の存在とinodeを照合できた移動だけを `rclone moveto` に渡す。移動後のパスにも内容確認を予約するため、編集と改名が重なっても両方を処理する。directory移動では移動対象の子ファイルを既存scopeで選び、除外ファイルは移動元に残す。既存の移動先は上書きを許す。対応が不明な移動は作成・削除の規則へ戻すか、破壊的な処理を保留する。scope外への転送はしない。

PlatformSpecific・Overflow・root変更・監視開始終了・API欠落などは再照合要求に変える。pCloud `/diff` のdiffid・file ID・modified・size・event timeをキューへ保持する。自己イベントはパスだけで捨てず、現在の両側内容を比較して一致した世代のみ完了させる。古いパス正規化では表現できない特殊名のAPIイベントは、別名へ誤変換せずrclone再照合へ回す。

通常転送は方向別の `rclone copy --files-from0 --no-traverse --ignore-times` とする。`--files-from0` はrclone filterに優先するため、ラッパー側で既存scopeを適用した対象だけを渡す。並列転送、再試行、転送ログはrcloneが担当する。転送時のlocal backendはrclone通常設定の `--local-encoding Slash,InvalidUtf8,Dot` を明示する。managerはUTF-8の対応範囲で公式のStandard/local変換を合成する最小の境界処理だけを行う。全角「／」・引用付き「／」・全角dotを保持し、往復できない表記を別名に正規化しない。ローカル全件の名前発見に限りRawで実名を取得し、転送前に往復対応を検証する。

downloadはstate配下へstageし、cloud版・元のlocal版・取得内容を再検証する。既存localは退避後、同じlocal volumeの一時ファイルから置換する。uploadも終了後に内容とlocal版を照合する。batchの終了コードだけを成功判定にせず、検証できた項目のキュー世代だけを消費する。後着イベントは残す。未完了child・attemptは従来の復旧手続きが完了するまで実行を止める。pushdとdiffdのexecutorは同じtick lockを順番に取り、一つの同期エンジンを実行する。

## 確認画面とCLI

xbarの「同期の確認待ち」から既存pywebview画面を開く。通常の新しい版は自動同期し、同秒の内容差、削除対編集、情報不足などの例外だけを表示する。列のフィルタ・並べ替え、一括採用、Quick Look、既定アプリで開く操作は維持する。

公開CLIは従来と同じ `diffd transfer manual list|preview|apply`、`diffd transfer manual batch preview|apply --input FILE|- --json`。入力schemaは `pcloud-manual-batch.v1`、choiceは `pull`・`local`・`hold`。UIは採用判定を実装せず、このCLIを呼ぶだけとする。

確認tokenはscopeの再検証、両側の版、設定先、キュー世代に結び付く。確認後に変わった項目は再確認する。同秒競合は明示的に選んだ版を反映する。削除対編集では残っている側を選んで復元できる。存在しない側の採用を削除命令として扱わない。未確定移動はこの採用操作では解消せず、復旧確認を要求する。手動採用の上書き前には旧版を退避する。複数項目の途中失敗では後続を自動適用しない。

## 保存場所と運用

以下は設定されたstate directoryを基準とする。ファイル本文・個別パスを含む実行記録は公開しない。

- `event-sync/state.json`: 最終同期版、確認待ち、再照合の残件、書き込み待ち、処理順。
- `event-sync/reconcile-request.json`: 再照合要求の世代と理由。
- `event-sync/receipts/<attempt>/`: 退避local・手動採用前のcloud・download stage。自動削除しない。
- 従来のpushd/diffd attempt journal: child終了確認、完了・復旧状態。イベント同期の転送attemptはpushd側に記録する。

status・一覧表示は保存済みstateを使い、画面を開くためにクラウド全件へ問い合わせない。確認待ちは処理順を循環させ、先頭の保留だけで新しい項目が処理されなくなることを防ぐ。大規模な初回再照合では残件がゼロになるまで複数tickを使う。`--max-records` は1tickの件数上限、既存のtimeoutはrclone子コマンド単位の上限である。

## pcloud-archive

archiveの一方向転送scopeは変更しない。既存rclone configで接続先のbackend typeが `crypt` と確認できる場合、検証を `rclone cryptcheck --one-way` に切り替える。暗号化先に通常の `check` を使うと平文とのハッシュ比較にならないためである。通常backendは従来の `check` を使う。暗号化されたrclone configやinline/environmentだけのremote定義でtypeを読めない場合は自動識別の対象外であり、通常checkによる内容一致の保証を拡大解釈しない。

## 検証と配備

意思決定表、同秒差、両側編集、自己通知と後着編集、初回片側、走査中の世代、live削除対編集、部分成功、download中のlocal変更、未完了attempt、編集と改名、除外子ファイル、手動採用token、実行gateをfixtureで検証する。macOS実機のfswatchと一時local backendのrcloneも使う。本番ファイルの破壊的な試験は行わない。

完成candidateのsource hash、テスト結果、wheel hashを結び付け、独立Reviewerの確認後に非editable wheelを配備する。既存manual設定からeventへの切替、executorのbatch上限、子コマンドtimeoutは元設定とplistのbackupを取って記録する。起動後はinstalled import先・設定・4サービス・復旧待ち・再照合状況を読み取り確認する。

## 初回照合の取得量（0.3.1）

初回はrcloneの再帰一覧で対象名を集める。この段階では `--hash` を付けず、ローカル一覧も同じfilterを渡したrcloneに任せる。リストの保存後、tickごとの上限で選んだ項目だけ内容ハッシュを取得して従来の判断・検証を行う。全件のハッシュ取得を初期化の前提にしない。選択対象の内容比較と、移動後の内容検証は省略しない。一覧取得の失敗時は未取得を不在扱いせず、保存前のキュー世代を残す。

launchdの環境変数は `.env` に優先する。配備確認ではplistに設定された子コマンドtimeoutも確認し、設定ファイルだけを見て実行時の制限と断定しない。

旧Raw前提のdecoderが全角「／」を区切り文字へ読み替えていた問題を修正した。実際のクラウド12件はAPI実名・rclone出力・file IDが一致し、うち10件は同名のローカル通常ファイルが存在した。旧保留は元のcloud file IDと現在の対応が一致した項目だけ既存照合の先頭へ戻す。照合の残件・捕捉済み世代・後着イベントを破棄しない。対応やmetadataが未取得なら保留し、不在と扱わず改名を要求しない。非可逆な表記や重複した転送先は成功扱いしない。

再照合中は対象一覧を先に永続化し、進捗の保存は1batchごとに行う。途中停止では未完了一覧から再検証する。走査開始後に届いたキュー世代は消費しない。通常同期・手動採用では従来どおり、検証結果の保存後に対象世代だけを消費する。大きい対象一覧の全体を1件ずつ書き直す処理を避ける。

改名・移動の対象探索も名前の一覧で行い、移動するファイルだけ直前にハッシュを取得する。未知の内容ハッシュでは移動を開始せず、移動後の内容一致を検証してから完了する。対象外のクラウドファイルのハッシュ取得を改名処理の前提にしない。


## 状態スナップショットと診断（0.3.2）

イベント同期の現在の入口は `status --detail --json`。0.3.2ではCLIが `pcloud-event-status.v1` を集約し、xbarはその保存キャッシュを表示する。初回照合の保存残件・確認待ち件数・保存日時と、取得時点のexecutor稼働を区別する。未取得は未取得、古い保存状態は更新待ちとし、全件一致や同期完了を推測しない。確認画面の件数も同じScopeと保存stateから計算し、取得した版の保存時刻を表示する。画面更新でクラウドの走査・ハッシュ取得は行わない。

メニューは「同期の確認待ち → 確認待ちを開く…」「状態の詳細」「診断」「Mounts」。要操作の重複入口、Mode、独立Push/Pull、調査用Preview、Shortcuts、一括mount/unmountは表示しない。vault/cryptの個別操作とxbar本体の末尾メニューは維持する。CLIの既存コマンドは廃止しない。旧bisyncの起動やサービス停止など実際の異常は状態に残す。

`state.json`を一度読み、`updated_at`を版・保存時刻として残件と確認待ちを集計する。実行状態は両executorの実際のtick lock、取得時刻は別のobserved_atを使う。queueは待機イベント数としてそれぞれの保存時刻を付ける。`event-sync/operation.json`は実行開始・前回終了・成功/失敗とaction別件数を記録し、次batch中も前回結果を保持する。成功はその処理の終了であり全同期完了ではない。stateが120秒を超えて古い場合、稼働中の初回照合では保存時点の値と明示し、待機時には更新待ちとする。

名前の検証は実rcloneのlocal backend同士と、pCloudと同じencodingをconnection stringで固定したfixtureで行う。後者はグローバルlocal-encodingで上書きしない。全角slash・引用・改行・dotを含む往復、対象外子の保持、native controlと記号が同じ転送名に衝突する場合の拒否を確認する。実機の対象12件についてはmetadataを読むだけで、名前変更・破壊的転送の試験はしない。

診断画面はpcloud-statusの既存pywebview hostを再利用する。CLI doctorの出力を文字列として表示し、操作名・開始終了時刻・実行中/成功/失敗・コピーを提供する。前回表示はキャッシュを読むだけ。GUIのbridge/DOMとネイティブhost起動・singleton socketの動作を検証する。CUA native接続はtimeoutのため実画面の目視は未検証であり、機能試験と区別する。

APIイベントのremote_file_idがある場合は、取得済みの対象cloud IDと照合する。cloud削除時は保存baselineのcloud IDを使う。一致・不在確認ができなければ当該イベントを保留し、別のオブジェクトへ読み替えない。追加の全件照合やmetadata要求はしない。
