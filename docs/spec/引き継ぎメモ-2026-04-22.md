## 現在の問題意識

- `pcloud-manager` が肥大化している
- `bisync` は毎回 `Building Path1 and Path2 listings` と `Checks/Listed` に長時間かかる
- 1MB 程度の更新でも、反映待ち時間の本体は upload ではなく全体走査
- 直近ログでは successful run でも 70 分前後が listing/checking に使われている

## 運用方針の整理

- pCloud は Dropbox 代替の「常時双方向編集」ではなく「保管庫」として使う
- 家の Mac で編集した変更は即反映したい
- 外での編集は例外
- 双方向で軽く編集するものは iCloud に寄せる
- remote 側変更は自動 merge ではなく「検知して通知」が基本

## 次にやること

### 1. リファクタリング

新しい実装本体を `~/p-core/dev/pcloud-tools/` に分離する。

想定:

- `~/p-core/dev/pcloud-tools/pcloud-manager`
- `~/p-core/dev/pcloud-tools/pcloud-sync`
- `~/p-core/dev/pcloud-tools/pcloud-pushd`
- `~/p-core/dev/pcloud-tools/pcloud-diffd`
- `~/p-core/dev/pcloud-tools/lib/...`

入口コマンドは `~/p-core/bin/pcloud-manager` に置く。

方針:

- `pcloud-manager` は user-facing entrypoint / dispatcher
- 実装詳細は `dev/pcloud-tools` 配下に移す

### 2. 新機能

`bisync` は本線から降ろし、保険機能として残す。

本線候補:

- `fswatch` ベースの local change -> immediate push
- pCloud API `diff` + `block=1` による long-poll
- remote change 検知時の通知
- 必要なら将来 option で auto download

## pCloud API 調査結果

- 典型的な webhook は docs 上見当たらない
- 代わりに `diff` API がある
- `diffid` を保持して `block=1` で long-poll 可能
- 変更イベントは `modifyfile`, `createfile`, `deletefile` など
- webhook より、`diffid` ベースで取りこぼし補完しやすい設計

## 新アーキテクチャ案

- `pcloud-manager`
  - 人間が叩く入口
  - status / doctor / command dispatch
- `pcloud-sync`
  - 現行 bisync 系の保険コマンド
- `pcloud-pushd`
  - local watcher
  - fswatch -> upload
- `pcloud-diffd`
  - remote watcher
  - `diffid` long-poll -> notify

## 実装時の重要論点

- `pcloud-manager` にどこまで logic を残すか
- `pcloud-pushd` の debounce / batch 設計
- `pcloud-diffd` の `diffid` 永続化先
- remote change を見つけた path の扱い
  - notify only
  - local push freeze
  - manual reconcile 導線

## 既存機能で残すべきもの

- `status`
- `status --detail`
- `doctor`
- `sync status`

- `sync scope`
- `sync check-allowlist`
